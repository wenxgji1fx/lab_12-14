# Лабораторная работа 14

Тема: управление жизненным циклом `DbContext` в MVVM-приложениях.

Проект: WPF-приложение «Телефонная книга» на .NET 8 с Entity Framework Core и SQLite.

## Цель работы

Изучить проблемы некорректного времени жизни `DbContext` в десктопных MVVM-приложениях, освоить `IDbContextFactory`, работу с отсоединёнными сущностями и безопасную реализацию CRUD-операций без накопления состояния в Change Tracker.

## Что изменено

- Регистрация `AddDbContext<PhoneBookDbContext>` заменена на `AddDbContextFactory<PhoneBookDbContext>` в `App.xaml.cs`.
- `ContactsListViewModel` и `ContactEditViewModel` получают `IDbContextFactory<PhoneBookDbContext>`, а не сам контекст.
- Операция чтения создаёт локальный контекст через `using var context = _contextFactory.CreateDbContext()`.
- Операция создания создаёт локальный контекст, добавляет сущность и вызывает `SaveChanges()`.
- Операция редактирования реализована через паттерн Fetch-Modify-Save: новый контекст находит актуальную сущность по `Id`, переносит значения из формы и сохраняет изменения.
- Операция удаления создаёт новый контекст, находит контакт по `Id`, удаляет его и сохраняет изменения.
- После каждой операции список контактов перечитывается из базы данных, поэтому UI получает актуальные данные.

## Контрольные вопросы

1. Захваченная зависимость возникает, когда долгоживущий объект удерживает короткоживущую зависимость. В WPF ViewModel может жить всё время работы окна, поэтому внедрённый напрямую `Scoped DbContext` тоже начинает жить слишком долго.
2. `IServiceScopeFactory` создаёт scope и достаёт зависимости из контейнера, но это приближает ViewModel к Service Locator. `IDbContextFactory` явно показывает зависимость ViewModel от фабрики контекстов и создаёт только `DbContext`, который нужен для операции.
3. При использовании `IDbContextFactory` контекст создаётся внутри конкретной операции и уничтожается после выхода из `using`. Загруженные сущности после уничтожения контекста становятся отсоединёнными, потому что Change Tracker больше их не отслеживает.
4. Паттерн Fetch-Modify-Save означает: найти актуальную сущность в новом контексте, изменить её свойства и вызвать `SaveChanges()`. Такой подход предпочтительнее `context.Update()`, потому что изменёнными будут только реально поменянные поля, а не вся сущность целиком.
5. Долгоживущий `DbContext` накапливает отслеживаемые сущности, увеличивает потребление памяти, может показывать устаревшие данные из Change Tracker и со временем замедлять работу приложения.
